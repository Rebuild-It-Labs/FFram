    Research Guide¶

    This guide outlines the methodology, experimental design, and reproducibility steps required to produce a rigorous IEEE‑style paper for the FFram project.

    1. Research Questions¶

    1. RQ1 – Probing Efficiency: Does native container probing (via PyAV) reduce metadata extraction latency compared to a ffprobe subprocess?
    2. RQ2 – Quality‑Targeted Encoding: Can an automated VMAF‑driven CRF search (Auto‑CRF) reliably achieve a perceptual quality floor while controlling output size?
    3. RQ3 – Parallel Cluster Gains: What speedup does the lightweight XML‑RPC cluster provide relative to single‑node execution?
    4. RQ4 – Fault‑Tolerant Execution: Can rule‑based heuristics recover from out‑of‑memory and GPU‑encoder failures without manual intervention?

    2. Experimental Setup¶

    • Hardware: Single workstation (CPU cores, optional GPU). All experiments run on the same machine to isolate algorithmic effects.
    • Software Stack: Python 3.11, FFmpeg with libvmaf, PyAV, standard‑library xmlrpc.
    • Benchmarks:
    • Metadata probe: 20 iterations of a 1‑second synthetic clip.
    • Auto‑CRF: Two synthetic clips (high‑motion, low‑motion) encoded with static CRF 23 and Auto‑CRF targeting VMAF 95.
    • Cluster: Two worker nodes on ports 8001/8002 processing a 4K clip via a segment‑encode‑concatenate pipeline.
    • Resiliency: Fault injection via unittest.mock for OOM and NVENC failures.
    • Metrics: Latency (ms), VMAF score, output size (KB), speedup, efficiency, and success/failure of recovery.

    3. Data Collection & Analysis¶

    • Use time.perf_counter for latency measurements.
    • Compute VMAF with libvmaf; report mean ± SD.
    • Size change: (\Delta S = (S_{auto} - S_{static}) / S_{static}).
    • For the cluster, calculate speedup (S(p) = T_1 / T_p) and efficiency (E = S(p) / p).
    • Summarize fault‑injection outcomes (recovery applied vs. not).

    4. Reporting Conventions¶

    • Present results in tables and figures with clear captions.
    • Include confidence intervals where appropriate.
    • Discuss internal and external validity threats.
    • Highlight any missing data (e.g., unavailable 4K test video) and its impact on reproducibility.

    5. Reproducibility Checklist¶

    • All benchmark scripts are version‑controlled (see website_docs/reference/benchmarks.md).
    • Exact command lines and library versions are listed in the Environment table.
    • Random seeds are fixed for deterministic behaviour where applicable.
    • Raw output logs are archived in the repository's benchmarks/logs/ folder.

    Use this guide as a template when extending the paper or adding new experiments.
